hmharness 二十问

零 IDE 开发鸿蒙、命令行打包签名、hapsigntool 签名失败排查、CI/CD、hmh check 与 devices 首错分流、hmh mcp-serve 默认工具面、AI 防幻觉、自进化真实性、认知层学习曲线、ARC-AGI-3、手机远程——每个答案独立成块，AI 搜索引擎可直接摘引；每个说法附证据出处。

Q1hmharness 是什么？

一句话答案hmharness 是一个开源（MIT 协议）的鸿蒙 HarmonyOS/OpenHarmony 开发智能体框架：终端一句话跑通「建工程 → 构建 → 签名 → 装机 → 日志」全流程，不打开 DevEco Studio、不登录华为账号、模型任意换，且自带可审计的自进化机制。

安装即用：npm install -g @hmharness/cli（Node >= 22）→ hmh init → 配置任意 OpenAI 兼容厂商 → hmh "创建一个双页面工程，构建签名装到模拟器跑起来"。单仓 16 包（含 cognitive 认知层与 environments 环境适配）、内核 0 运行时依赖、1182 个单元测试门禁（最新 CI：1181 通过 / 1 跳过）；CLI / TUI / Web 三前端，zh/en 双语。

出处：README · 官网首页

Q2鸿蒙开发必须用 DevEco Studio 吗？

一句话答案不是必须。DevEco Studio 是官方主力 IDE，但开源的 hmharness 证明了零 IDE 路线：纯终端驱动官方无头工具链完成脚手架、构建、签名、装机、日志，模拟器全生命周期无头管理——适合脚本化、CI 化与 AI Agent 化场景。

hmharness 直接驱动官方无头 CLI：harmony_project_create（参数化多页面/多模块/feature HAP/har 库）→ harmony_build → harmony_sign → harmony_install/launch/logs；harmony_emulator_list|catalog|create|start|stop|delete 管理模拟器全系机型。与 DevEco 互补而非替代：日常图形开发用官方工具，自动化与 Agent 场景用 hmharness。

出处：README「鸿蒙全流程（零 IDE）」

Q3鸿蒙应用怎么用命令行打包和签名？

一句话答案用 hvigor 命令行构建 + hapsigntool 签名。hmharness 把两者封装成 harmony_build 与 harmony_sign 工具（自动定位 jar/p12/pem/模板/java 五件套），签好的 HAP 直接经 hdc 装机验证——整条链不打开 IDE。

实测踩坑记录（2026-09-05 DEVLOG）：hapsigntool 的 -mode 取 localSign（不是 debug/release）；SDK 自带调试证书模板有效期停在 2023 年（过期三年无人发现，由 hmharness 报错链一步步定位）；支持过期 profile 检测与刷新。官方文档未覆盖这些，破案过程全记录在案。

出处：DEVLOG 2026-09-05「签名五关」 · 速查表下载：signing-five-gates.pdf（A4 一页，可自由分发）

Q4鸿蒙 CI/CD 自动化构建打包怎么做？

一句话答案把 hvigor 构建、签名、hdc 装机、hilog 日志变成可调用工具即可脚本化。hmharness 全部封装完毕，支持审批门禁的非交互模式（默认拒绝、--yes/rules 放行、破坏性命令硬拒绝），可直接接 CI 流水线。

典型链路：harmony_project_create → harmony_build → harmony_sign → harmony_install → harmony_logs 回读断言。CI 里不需要华为账号登录（密钥只存本地配置），这是与官方工具链自动化路径的关键差异。

Q5有什么 AI 编程工具支持鸿蒙开发？

一句话答案两类可选：华为官方 DevEco Code（官方跟进最快，需登录华为账号）；开源 hmharness（MIT，不登录、任意 OpenAI 兼容模型、零 IDE 全流程 + 自进化）。hmharness 还能以 hmh mcp-serve 把鸿蒙工具链变成 Claude Code / Codex / Cursor 的原生 MCP 工具。

MCP 服务器模式只暴露 harmony_* 域工具（构建/装机/日志/签名/API 检索/雷达），通用文件与命令工具不暴露（宿主有自己的）；宿主权限系统负责问用户，server 侧破坏性硬墙永驻。两种用法互补：要自进化用原生 hmh 会话，要借力现有编码 Agent 用 MCP 模式。

Q6怎么防止 AI 编造不存在的鸿蒙 API？

一句话答案靠索引拦截，不靠模型自觉。hmharness 解析 SDK 927 个 d.ts 文件、索引 20,241 个 API 符号（实测 0.2 秒），harmony_api_lookup 查不到就返回「不在此 SDK，不要猜」——幻觉被索引拦截。

模型编造 ArkTS/ArkUI API 的根因是它看不见你的 SDK 版本；知识图谱按本机 SDK 实时构建、缓存于 HMH_HOME/apikg（SDK mtime 变化才重建），因此检索结果永远与本机 SDK 一致，而不是训练记忆。

出处：DEVLOG「API 知识图谱」

Q7hmharness 的「自进化」是真的吗？

一句话答案机制真实、效果诚实：技能晋升要过双门禁（A/B 双样本基准 + 防背题保留门）再进金丝雀（20% 会话对照），≥8 会话且 ≥10% 差才转正，回归即回滚。连续 3 个月公开数据集的结论是——零统计可靠晋升（门在正确拒绝噪声），但自暴露并修复了 7+8+0 个生产缺陷，月 3 首次出现跨尺度稳定正效应（真实但小）。

逐月事实：月 1 修复 7 个生产缺陷、零晋升；月 2 修复 8 个、门持续拒绝；月 3（2026-09-15 复盘）零生产缺陷、程序史首个 REJECT 行动判定、首个跨 4 报告 ×3 复现的正效应——恰好 1 个中文精确输出案例，不足以过 10% 门。「越用越聪明」尚未被证实，被证实的是门与审计面在正确工作；全部判定记录、被拒候选与原始日志原样公开。代码级自进化默认关闭，只允许改 packages/*/src/*.ts、永禁内核循环。

认知维度补充（2026-09/10 更新）：0.23.x 系列把「学习」拆到可测的校准维后，自进化首次有了持续为正的读数——预测可靠度学习曲线 terminal +5.9%、harmonyos +14.4%、browser +37.6%（无头 Chrome CDP 探索）、arc3 +76.2%（LLM 实玩轨迹，样本薄）均 improving，desktop 1.00 flat 是确定性工具的完美校准（hmh cognitive calibration --trend 可复现），迁移实验中校准差 +0.4166 为纯 harness 净贡献（LLM 未参与）。详见 Q11。

出处：SELFFEED 月 3 终局复盘 · 首月数据集

Q11hmharness 的认知层是什么？harness 真的从经验中学习吗？

一句话答案认知层是 hmharness 区别于普通 Agent 框架的核心增量：世界模型从每次任务的工具轨迹中学习并反哺系统提示；校准可靠度随使用提升——五环境曲线全有读数，四环境 improving。这不是宣称，是 hmh cognitive calibration --trend --env=terminal 的输出。

认知层包含世界模型（信念表+预测置信+误差聚类）、五层记忆（working/episodic/semantic/procedural/world，只增不删+溯源）、目标系统（图谱/分解/漂移检测）、探索引擎（不确定性×信息增益×校准导向）、技能编译（经验→可验证技能→门禁晋升）、进化 2.0 治理（候选契约/序贯门禁/reward-hacking 检测）。15 条 hmh cognitive 子命令全部可用。

研究定论（消融 11 轮）：单任务提示层 0 / 跨任务复利 0 / 校准维 +0.4166（唯一持续为正，LLM 未参与 = 纯 harness 净贡献） / 学习曲线五环境全有读数——terminal +5.9%、harmonyos +14.4%、browser +37.6%（无头 Chrome CDP 探索）、arc3 +76.2%（ARC-AGI-3 LLM 实玩轨迹，样本薄）均 improving，desktop 1.00 flat（确定性工具完美校准）。harness 的实证价值在让模型更准地预期世界，而非替模型答题。

出处：ROADMAP §26 研究终局表 · 官网认知层节

Q12ARC-AGI-3 是用来训练大模型的吗？

一句话答案不是。hmharness 的权重从不更新（微调走独立轨道，已收官）；ARC-AGI-3 是外部考官——衡量"固定模型 + 认知层"的组合在未知环境的表现。harness 的净贡献可以完全分离。

证据：迁移双臂实验中 LLM 完全未参与，校准差 +0.4166 是纯框架增量。学习环只走 harness 层（记忆/技能/工作流/世界模型），模型权重更新有最高证据门槛（0.95）且不通过 ARC 进行。视觉实玩 ARC 游戏（帧渲染→模型推理→reasoning 入档）测的是"固定模型+harness"的联合表现，通过消融实验可分离 harness 贡献。

Q13手机怎么远程控制 hmharness？

Q14AI 候选会靠「啰嗦」通过基准测试吗？怎么防？

一句话答案会，且真实发生过。hmharness 的防法是双保险：判卷用四种断言模式钉死输出形状（一字不差 / 正则 / 禁词表 / 多候选），再加成本门——候选输出 token 成本超过基线 1.3 倍且超出超过 8 个 token 即判「成本回归」，靠啰嗦刷分直接出局。

成本公式：cand > max(base × 1.3, base + 8)。token 估算按「中日韩字符≈1、ASCII≈1/4」——切回中文灌水同样绕不过帽。乘法帽曾把期望输出只有 4 个 token 的微型考题变成 Hair Trigger（余量仅 1 token，连续 10 个候选被误杀），+8 绝对余量地板修复了它——真啰嗦是 2-10 倍量级，针尖级扰动不该死。成本只否决不判分：通过率门仍是主判据，双指标各管一半。全部判定有 10 个单元测试守护（bench.ts / evolve.ts）。

出处：packages/evolution/src/evolve.ts · gate.test.ts · 速查表下载：ai-bench-anticheat.pdf（A4 一页，可自由分发）

Q15Agent 怎么记住踩过的坑？记错了怎么办？

一句话答案hmharness 的记忆检索是计分制不是全文匹配：置信度 ×0.4 + 新鲜度 ×0.2 + 词法相关 ×0.4，查询先分词再部分计分——检索「hvigor build windows」这类带无关词的查询也能命中该命中的经验，硬过滤条件不变。

旧方案 AND 子串匹配会在查询里混入无关词时全部漏检（旧 AND 检索 miss 的根因）；计分检索允许部分词法得分，排序公式在 memory.retrieve 中可审计。五层记忆（working/episodic/semantic/procedural/world）只增不删、每条带溯源——记错可查证，标记可追踪。工作区隔离用标签制：本区记忆 ×2.5 加权，他区降权 ×0.3 但不消失。

出处：CHANGELOG 0.23.26（memory.retrieve） · ARCHITECTURE 认知层

Q17hapsigntool 签名失败怎么逐项排查？

一句话答案不要把签名失败当玄学。先拿 hapsigntool -h、verify-profile 和 keytool 的真实输出，再按模式词、证书有效期、key alias、证书链、Windows 路径五关排查。
  1. 模式词：-mode 使用 localSign，不是 debug 或 release。
  2. 证书有效期：用 verify-profile 读取 not-before/not-after 数字；SDK 调试模板曾停在 2023 年，过期时复制模板刷新有效期并更换 uuid。
  3. key alias：用 keytool 列出 PKCS12 内别名。实测 sign-app 使用 openharmony application profile debug，不是直觉的 application release。
  4. 证书链：appCertFile 使用 OpenHarmonyProfileDebug.pem 的三级证书链，不要混用 OpenHarmony.p12 或 Profile pem。
  5. Windows 路径：hdc install 使用反斜杠路径；正斜杠会被当成相对路径拼接。

签名成功还不是终点：继续 install → launch → hilog，回读到生命周期标记才算设备闭环。hmharness 的 harmony_sign 封装 jar/p12/pem/模板/java 五件定位与过期 profile 刷新，把这条证据链固化成工具。

出处：DEVLOG 2026-09-05「签名封装+设备测试」 · signing-five-gates.pdf

Q18CI 显示全绿也可能是「假绿」？怎么识别和修复？

一句话答案会。hmharness 曾连续 13 天 CI 假绿：库里一条无条件的 process.exit(0) 在断言跑完前击杀了测试宿主进程——CI 收到零退出码就判通过，五个潜伏缺陷被掩盖。修复 = 移除库内 process.exit + close 幂等化，另加 clean-room 发版验真自动化。

假绿的鉴别特征：文件级失败但没有逐条测试结果——"全绿"可能只是"没跑到断言就被杀"。本机与 CI 同代码不同红绿，出问题的是裁判本身。

修复三件套：①统一句柄登记表，closeOnce() 按 LIFO 排干全部句柄，closed 标志门住写入侧；②库层代码绝不调用 process.exit，close 保持幂等；③回归测试钉死合同：挂起的连接被终止后进程必须还活着。

发版验真：补用例救不了退出码失真——验证通道本身不可信时，新用例只是被绕过的代码。hmharness 用 clean-room 发版验真：官方源 tarball 双指纹校验 → 全新目录隔离安装 → 15 包钉版核验 → 关键路径实跑 → 工件脱敏归档，11 个验真用例接进 npm test。修完 1037 个测试第一次真正全绿。

自查三信号：①基础库里 grep 无条件 process.exit；②测试与被测对象是否共进程（共进程=共命运）；③发版验证是否跑在 CI 同一环境（同环境=同盲区）。

出处：DEVLOG 2026-10-29「测试诚实化双收官：CI 假绿根修 + clean-room 验真自动化」 · CHANGELOG 0.23.45

Q19安装后 hmh check 或 hmh devices 失败怎么排查？

一句话答案先分四层：Node 版本、npm 包与 CLI 入口、无模型工具链探针、设备可见性。hmh check 不需要模型；hmh devices 返回无设备也不等于安装失败。
  1. 运行时：确认 Node >= 22。低于该版本先处理运行时，不进入工具链排查。
  2. 包与入口：npm list -g @hmharness/cli 能读到包，hmh --help 能执行；这一层只证明 npm 包和入口存在。
  3. 工具链：hmh check 直连 hdc、hvigorw、ohpm、cjpm，不需要模型 API key。缺 hdc、hvigorw 或 ohpm 时先安装或配置 SDK / DevEco CLI 后复跑；cjpm 探针失败是本机工具信号，不包装成通过。
  4. 设备可见性：hmh devices 无设备是启动模拟器或接入已授权设备前的合法状态；这一层失败不应倒推 npm 安装失败。

需要求助时打开环境 Issue 模板，按字段提交 OS、安装路线、npm list、脱敏 check/devices 输出和第一个卡点；不要粘贴 API key、cookie、私人路径或设备/账号标识。自由讨论仍可用 Discussion #4。

Q20hmh mcp-serve 默认暴露哪些工具？会不会绕过审批？

一句话答案不会绕过审批。hmh mcp-serve 是给 MCP 宿主使用的鸿蒙工具箱出口：默认只暴露 harmony_* 域工具，不暴露 run_command、write_file 等通用工具；每次调用由宿主权限系统确认，server 侧硬墙仍在。
  1. 默认工具面：构建、装机、日志、签名、API 检索、雷达等 harmony_* 域工具；宿主已有的通用命令与文件工具不重复暴露。
  2. 继续收窄：用 HMH_MCP_TOOLS 按需限制工具列表，例如只开放 harmony_build,harmony_ops。
  3. 审批位置：每次调用由 Claude Code、Codex、Cursor 等宿主自己的权限系统逐个确认；server 侧破坏性硬墙仍在。--yes 与 approval:auto 是显式扩大授权，不是安全证明。
  4. 观测边界：外部调用写入 insights/mcp-calls.jsonl，只做观测，不进入自进化门禁；记忆、技能和门禁只在原生 hmh 会话中运行。
