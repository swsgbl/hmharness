hmharness 如何约束 Prompt Injection

Prompt Injection 没有“一句话修复”。本页把 hmharness 在公开源码里已经落地的审批、硬拒、状态根保护和能力边界拆开，说明它降低的是什么风险，以及哪些风险仍然存在。

hmharness 是一个开源的 HarmonyOS/OpenHarmony 开发智能体框架：它把工程创建、检查、构建、签名、安装、启动、日志读取和结果验证接成本地工具链，让 AI 不只是生成代码，还要用本机环境证明结果；同时通过审批、预算、canary 和回滚约束自进化行为。它不是 DevEco Studio 的替代品，而是开发智能体和鸿蒙工具链之间的验证层。
本页只展开其中一环：不可信输入试图变成高危动作时，边界在哪里。
先说边界：hmharness 不解决 Prompt Injection。它没有宣称能识别所有藏在网页、文件、issue、工具输出或其他模型上下文里的恶意指令。这里的价值是纵深防御：即使模型被诱导，动作面也被拆成审批、路径、密钥、网络和 MCP 权限，多防线共同缩小爆炸半径。
四层边界分别是：1）动作先过审批，非交互默认拒绝；2）审批规则所在 HMH_HOME 永远审批，破坏性命令模式硬拒；3）能力访问 deny-by-default，网络和密钥可用 live grant 约束；4）外部 MCP 工具逐项门控，浏览器动作默认不暴露。auto 和 --yes 是显式扩大授权的例外，不是安全证明。

四层边界

这四层不是四个同义词：它们分别拦截“模型要行动”、“行动要改规则”、“行动要用能力”和“外部工具要接入”四类路径。

01审批门

run_command 与 write_file 需要审批；默认 ask 在 TTY 问 y/N，在非 TTY 中拒绝。测试覆盖 yes/auto/ask 三条路径。

02持久硬墙

盘根、系统目录、家目录递归删除等命令模式硬拒；HMH_HOME 内配置与审批规则永远审批，防止一次写入解除其他门。

03能力边界

Capability Broker 对能力访问 deny-by-default；grant 有期限和审计，网络可限定 allowedHosts，密钥只在 live grant 下换成真实值。

04MCP 边界

远端 MCP 工具投影后仍要求 needsApproval；浏览器扩展 MCP 默认只读三件，页面动作需 HMH_MCP_EXTENSION_ACT=1。

这套设计降低什么

  • 不可信文本不能直接等同于高权限工具调用。
  • 一次提示绕过还需要面对路径、命令、密钥、网络和 MCP 权限。
  • 审批规则本身被列为高影响状态，不能被普通工作区编辑静默改写。

它不消除什么

  • 模型仍可能被诱导生成错误分析或无害但浪费的调用。
  • --yes、approval:auto 和过度宽泛的授权会削弱交互门。
  • 模式匹配不是完整沙箱；高危环境仍要最小工作区、最小账号和隔离运行。

建议部署姿势

默认跑法

  • 保持默认 ask，让写入、执行和外发副作用逐次确认。
  • 把模型可见的网页、issue、文件内容当作数据，不当作新的系统指令。
  • CI 或服务进程使用非交互路径时，接受默认拒绝而不是自动放行。
  • 密钥留在 HMH_HOME 或环境变量，不进入仓库、日志和模型上下文。

升级授权时

  • 只为具体工具、资源和时间段发 grant，避免长期通配授权。
  • MCP server 只在理解其工具面和权限要求后加入信任。
  • 启用 auto 前先确认失败成本、回滚路径和审计位置。
  • 浏览器页面动作保持默认关闭，确需启用时使用专用浏览器上下文。
