OpenHarmony 生态雷达如何避免过时建议

生态建议最常见的失败不是模型不会总结，而是它拿到的是旧世界。本页把 hmharness 生态雷达拆成四层可验证防线，并用一次独立的四源 API 读回展示为什么 HTTP 200 不能当 freshness。

hmharness 是一个开源的 HarmonyOS/OpenHarmony 开发智能体框架：它把工程创建、检查、构建、签名、安装、启动、日志读取和结果验证接成本地工具链，让 AI 不只是生成代码，还要用本机环境证明结果；同时通过审批、预算、canary 和回滚约束自进化行为。它不是 DevEco Studio 的替代品，而是开发智能体和鸿蒙工具链之间的验证层。
本页只展开其中一环：生态雷达如何防止建议建立在上游生态的旧状态上。
不要把“拉到了数据”当成“数据仍在更新”。hmharness 的答案是四层防线：条目级快照 diff、90 天源新鲜度门禁、14 天简报有效期、外发动作人工审批。2026-11-18 的独立读回里，四个默认 GitHub feed 有三个 fresh，一个被判定 STALE；这正好说明为什么 freshness 必须单独验收。

四层防线

这四层分别处理不同错误：没有 diff 会重复读旧闻；HTTP 成功会掩盖死数据；旧简报会污染进化上下文；缺少审批会把误读变成外部动作。

01快照 diff

每次扫描保存已见条目 ID，下次只把新 ID 交给简报生成，避免把旧提交反复当新闻。

02源新鲜度

请求成功之外，还检查最新条目日期；超过 90 天标记 STALE，单个源失败不拖垮整个扫描。

03简报有效期

进化循环只读 14 天内最新简报；过期简报返回空信号，不能继续充当生态上下文。

04人工边界

AI 只起草 issue/PR 或通知；发布属于可见副作用，必须经过审批，不允许生态信号自动外发。

从扫描到建议的门禁流程

  1. 并行拉取每个源的公开条目；每个请求有超时，单源失败只记录错误，不让其他源失效。
  2. 第一次扫描建立基线，不做变更分析；后续扫描按 ID 与快照比较，只输出新条目。
  3. 读取最新条目日期并复算 90 天阈值；无日期或过旧都按失败源处理。
  4. 模型不可达时降级为模板简报，并显式保留源健康状态；不允许把降级输出包装成模型分析。
  5. 进化上下文只消费 14 天内简报，且只把它当环境信号，不当成本地工具链验证结果。
  6. 需要 issue、PR 或通知时进入审批边界；AI 起草，人确认后才外发。

它能证明什么

  • 每个生态结论都能回到条目 URL、日期、源配置和扫描记录。
  • 一个源静默死亡时会被显式标出，而不是变成“本期无变更”。
  • 模型不可达不影响读取和落盘，降级路径可见。

它不能证明什么

  • GitHub feed fresh 不等于该上游官方渠道没有更新。
  • radar 简报不替代本机 hmh check、构建、签名、安装和日志验证。
  • 生态信号不能自动证明某个兼容性建议已经适配用户当前 SDK。
